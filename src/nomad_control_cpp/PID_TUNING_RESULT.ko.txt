1. 사용하는 제어 방식
  GUI 목표 ERPM → C++ 목표 검증·가속/감속 제한 → ROS VESC 속도 명령
    → VESC 내부 속도 PID와 모터 전류 제어

  모드는 vesc_speed_pid이다. 단순 duty/PWM 목표로 바꾸거나 외부 C++ PID를
  중첩하지 않았다. VESC의 기존 속도 피드백 제어를 사용한다.
  조향은 별도 서보 위치 명령이다. 실제 바퀴 각도 센서는 없으며 GUI rad 입력은
  서보 명령으로 임시 환산된다. 모터 PID 보정과 구분한다.

2. 900 ERPM 출발 조건의 원인과 설정 변경
  사용자 관찰은 '속도 슬라이더 목표가900일 때부터 회전 시작'이었다.
  이 값은 GUI 목표이며 바퀴 회전수 실측이나 지상 속도 보정값이 아니다.

  원래 VESC 5.03 설정:
    s_pid_min_erpm=900.0
    motor config signature=2525666056, body 길이484 bytes
    필드 body offset357~360, float32_auto
    원본: /home/user/vesc_ws/backups/20261106_120405/motor_payload.bin
    로컬 해석: tmp/nomad_start_threshold/decoded_motor_config.json

  VESC 5.03에는 이 최소값 미만의 목표에서 속도 PID를 초기화하고 속도 구동을
  수행하지 않는 경로가 있다. 확인한 설정은 사용자 관찰과 일치한다.
  C++/GUI에900을 더하는 offset이나 목표를900으로 올리는 보정은 넣지 않았다.

  변경: s_pid_min_erpm 900.0→50.0, GUI 속도 입력 간격50 ERPM.
  50은 펌웨어가 속도 제어를 허용하는 설정값이다. 실제 모터·구동계가 안정적으로
  유지할 수 있는 최소 회전수라는 뜻은 아니다. C++에도 양수 목표를50으로
  끌어올리는 별도 최소값 보정은 추가하지 않았다.

3. 백업·재조회와 첫 번째 쓰기의 추가 바이트 변화
  첫 번째 시도:

  요청 payload는 최소 ERPM 필드만 변경했다. 실제 재조회에서는 body357/358
  이외에 body303이0xF2→0xF3으로 바뀌어 엄격 비교에 실패했다.
  이는 foc_voltage_offsets[1]의 직렬화된16비트 값에 해당한다.
    요청 전 wire: FF F2, 정수-14, 스케일10000 기준-0.0014
    재조회 wire: FF F3, 정수-13, 스케일10000 기준-0.0013
  공식 float16 직렬화의 부동소수점 왕복·정수 절삭으로 설명되는1단위 변화다.
  여기서 float16은 스케일 정수 형식이며 IEEE half와 다르다.

  실패 후 원본을 다시 쓰자 최소값은900으로 복원됐지만 body303은F3으로 남았다.
  따라서 원본 전체 바이트가 완전히 복구됐다고 주장하지 않는다.
  로컬 before/proposed/after/rollback payload 비교로 이 차이를 확인했다.
  첫 시도의 추가 변화는 다른 필드의 정규화로 별도 기록하며 숨기지 않는다.

4. C++ 제어와 GUI 변경
  - 제어 주기20Hz→50Hz, 상태 발행5Hz→10Hz.
  - GUI 드래그 입력은 최신 값으로 합쳐 최대20Hz로 전송한다.
    같은 UPDATE 응답 대기 중에는 UPDATE를 중복 전송하지 않는다.
  - ROS graph 조회 결과는100ms 미만 동안만 재사용한다.
    START는 캐시 없이 단독 드라이버 연결을 새로 검사한다.
  - 가속 제한1200 ERPM/s, 양수 목표로 낮출 때 감속 제한2400 ERPM/s.
  - 목표 정확히0을 수신하면 다음 제어 주기에0A 해제한다.
    저속 PID 명령을 서서히 내려 보내는 구간을 남기지 않는다.
  - STOP은 GUI UPDATE 대기열을 우회한다. 종료 세션은 다시 살아나지 않는다.
    수동 재시작은 항상 모터 목표0부터 시작한다.
  - GUI는 펌웨어 최소값 조회 확인 상태가true인 제어기에서만 시작을 허용한다.
    YAML 기본 verified는false이며 시작 스크립트가 실제 조회 후 설정한다.

  유지한 한계·정지 조건:
    모터 목표0~1850 ERPM, telemetry 과속 한계2500 ERPM, 전류 한계30A
    telemetry timeout0.30s, 제어 지연 한계0.20s
    기본 GUI 통신 만료0.35s. 현재 공중 Wi-Fi 연속 MANUAL 후보만 발행 시각 기준2.0s.
    공중 시험 설정 확인, 정지 유지0.50s, 단독 드라이버 연결 확인
    VESC 통신 timeout300ms 후0A

  추가한 정체 감시:
    요청 목표와 실제 송신 명령이 모두50 ERPM 이상이고,
    abs(telemetry ERPM)<50이 연속2초 유지되면 FAULT·0A 해제한다.
    초기 가속 중 송신 명령이50 미만인 시간은 세지 않는다.
    목표0 또는 회전수 조건 회복 시 정체 시간을 초기화한다.
    클래스 기본값은 비활성이고 commissioning.yaml에서는 활성화했다.
    피드백이 간헐적으로50을 넘는 진동까지 모두 판별하는 기능은 아니다.

  0A는 coast이다. 능동 정지 제동이 아니므로 관성 회전이 남을 수 있다.
  STOP 때 새 서보 위치를 보내거나 자동으로 중앙에 복귀시키지 않는다.

5. 조향 입력 범위
  실제 각도 보정은 미완료이며 calibration_verified=false를 유지했다.
  기존0.25 servo/rad 비율을 유지하며 서보 후보 범위를 실제로 넓혔다.

    GUI 입력(rad)    서보 목표
       -0.50          0.375
       -0.40          0.400
        0.00          0.500  (중립 후보)
       +0.40          0.600
       +0.50          0.625
       -0.55          0.3625  (다음 후보, 아직 실차 검증 전)
       +0.55          0.6375  (다음 후보, 아직 실차 검증 전)

  ±0.5 rad의 약±28.6° 표시는 입력 눈금이다. 실제 타이어가 그 각도까지
  꺾인다는 측정 결과는 아니다. 기계적 최대 조향각과 좌우 방향도 미보정이다.
  GUI는 서버의 steering_input_limit_rad와 servo_min/center/max를 사용한다.
  연속 수동 서보 명령 변화율0.40/s는 실제 바퀴 각속도가 아니다.

  사용자는±0.5 양 끝의 부드러운 동작, 눈에 띄는 간섭과 힘주는 소리의 부재를
  추가 확인했다. 이는 그 시험 조건의 동작 관찰이며 기계적 최대각 보정은 아니다.
  다음 후보±0.55 rad와 서보0.3625~0.6375를 Pi에 배포했다.
  0.25 servo/rad 임시 비율을 유지하므로 기존±0.5 입력 대응은 달라지지 않는다.
  새 후보±0.55의 입력상 약±31.5°를 실제 타이어 측정각으로 해석하지 않는다.
  새 후보의 소프트웨어 빌드·배포는 완료했고 양 끝의 실제 동작 검증은 아직 대기다.
  steering_input_limit_rad는 설정값으로 바꾸고0보다 크고0.55 이하인지 검증한다.
  raw 코어의 최대 허용 후보 범위도0.3625~0.6375로 제한했다.

  사용자는 바퀴를 공중에 띄운 상태에서 직접 GUI를 조작하고 다음을 보고했다.
    목표 약550 ERPM부터 부드럽게 회전하기 시작함.
    550보다 낮은 목표에서는 회전하지 않거나 덜컥거림.

  약550은 해당 조건의 GUI 목표 기준으로 관찰한 대략적인 출발 임계값이다.
  센서 피드백 수치나 지상 하중 조건의 최저속도 측정값이 아니다.
  해당 구간에서 목표·피드백 ERPM·전류를 동기화한 정량 기록은 없다.
  출발 뒤 속도를 낮춰도 회전을 유지하는 최저 목표는 아직 별도로 시험하지 않았다.
  출발 임계값과 회전 중 유지 가능한 최저 목표는 다른 항목으로 측정해야 한다.
  이 관찰만으로 약550을 자동 최소 목표나 고정 offset으로 적용하지 않았다.
  앞선 두 차례200 ERPM 제한 시간 시험은 여전히 사용자가 직접 보지 못한 시험이다.
  이후 수동 관찰로 그 두 시험의 물리 반응을 소급 확정하지 않는다.

  추가 수정 전 수동 시험 후 상태 조회: STOPPED_OUTPUT, 목표0 ERPM, 전류0A, VESC fault0.
  이 조회 시점은 조향 입력±0.5 rad, 서보0.375~0.625 버전이었다.
  새 버전은 observed_smooth_start_erpm=550과 설명을 상태에 표시하되 제어 목표는
  바꾸지 않는다. 기본값0은 관찰값 미설정이며550을 자동 하한으로 쓰지 않는다.

8. MANUAL 자동 해제의 확인된 이유와 GUI/HTTP 추가 수정
  연속 MANUAL(duration=0)이 시작 후 약8.75초와57.7초에 해제된 로그를 확인했다.
  이유는 'raw GUI command timeout'으로, 마지막 GUI 갱신 이후350ms를 초과한
  것이며3초 단기 시험 타이머가 아니다. 연속 모드에 새 총시간 제한을 넣지 않았다.

  별도 회귀 시험에서 기존 HTTP 서버의 idle keep-alive 연결4개가 worker를
  차지하면 인증된 STOP 요청도 처리하지 못하는 문제를 재현했다.
  이 결과는 지연을 일으킬 수 있는 서버 문제를 확인한 것이다. 두 실차 해제의
  모든 패킷·스케줄을 추적한 것이 아니므로 각각의 원인을 하나로 단정하지 않는다.

  2초 통신 후보 이전에 Pi에 반영한 변경:
    TCP_NODELAY와 keep_alive_max_count=1로 응답 완료 후 idle 연결의 worker 점유를 방지.
    heartbeat 간격50ms. 상태 조회는 경과 시간을 고려해 약100ms 주기로 예약.
    raw 연속 수동 제어는 보이는 창의 blur만으로 해제하지 않음.
    숨겨진 탭·pagehide·STOP·통신 이상에서는 계속 해제하고 자동 재시작하지 않음.
    누름 유지 모드의 blur 해제는 유지.
    명령 시각은 서로 양립하는 상태 요청/응답 표본의 보수적 하한으로 추정.
    Windows 벽시계나 임의의 RTT 보상은 더하지 않음. 상태 최신성 조건은 별도 검사.
    시계 변경·응답 재생·토큰 변경이 감지되면 세션을 해제하며 자동 재시작하지 않음.
    전역 STOP 응답과 그 이후에 시작한 최신 정지 상태 조회를 확인할 때까지 재시작 잠금.
    응답 대기 중 반복 STOP은 하나로 합치며 실패 시 잠금을 유지.
    이 단계에서는 서버 GUI 갱신 만료350ms, telemetry0.30초, 제어 지연0.20초 한계를 유지.

  위 수정 배포 후에도 실제 GUI 목표0 연속 시험에서 갱신 만료가 발생했다.
  이전 실패 결과는 tmp/nomad_continuous_fix/에 보존했다. 한 결과는 관찰 시작
  전에 이미 FAULT였으므로 실패 발생 시각·경로를 그 파일만으로 확정할 수 없다.

  추가 로컬 HTTP 수정:
    HTTP 첫 요청을 보내지 않은 TCP 연결4개/6개로 worker가 점유되는 경우를 재현.
    기존 코드16개 검사 중3개 실패: STOP 응답 제한과 초기 유휴 연결 만료 실패.
    worker8개·대기열8개로 제한하고 첫 요청 전 유휴 대기를5초에서1초로 줄임.
    수정 후16개 검사 통과, STOP 응답16.25ms/3.34ms.
    정상 브라우저 연결 수를 가정한 완화이며 모든 worker를 점유하는 과부하 보장은 아님.
    이 수정은 Pi 배포 후 전체8/8 검사, HTTP16개·ROS587개 통과.
    그러나 실제 목표0·서보0.5000 연속 시험은 관찰1.531초/4표본에 갱신 만료로 실패.
    제어기 로그는 START 후 약1.462초에 FAULT. 저장된 목표·송신 ERPM0, 전류0A.

  연결 재사용 비교와 GUI 서버 시각 추정 개선:
    worker8개·대기열8개·유휴 대기1초를 유지하고 연결당 최대 요청1개→32개.
    TCP/SSH 연결 생성 빈도를 줄이기 위한 후보이며 실제 개선 효과는 시험으로 확인한다.
    Windows/Pi 전체8/8·HTTP18개 검사 통과. 해당 Pi ROS 검사는593개.
    제어기 수락 UPDATE 간격150ms 초과, GUI bridge 처리 지연·명령 나이·거절 및
    시간 초과를 진단 로그로 기록하도록 추가. 명령 의미와 만료 조건은 변경하지 않음.
    GUI 서버 시각 추정은 최근1초의 양립하는 표본에서 보수적 하한을 사용하도록 개선.
    가짜 GUI 검사148개 및 Windows 전체8/8 통과 후 Pi에 배포.
    실제 목표0·서보0.5000 시험은11개 표본을 수집한 뒤 상태 조회1초 제한을 초과해
    관찰6.576초에 실패.90초 연속 합격이 아니다.
    Pi GUI bridge 진단: 수락 명령 나이260.5ms·처리5.3ms, 다음 거절 명령
    나이1258.6ms·처리0ms. 이 지연을 ROS 처리 시간만으로 설명할 수 없다.
    명령 나이는 보수적 서버 시각 추정 기준이며 단방향 네트워크 지연 실측값이 아니다.
    브라우저 전송·SSH 터널·네트워크·HTTP 대기 중 어느 구간인지 아직 확정하지 않았다.
    SSH IPQoS·압축의 읽기 전용 비교에서는 확실한 개선을 확인하지 못함.
    추가8766 터널은 종료, 기존8765 설정 유지. 추가 네트워크 진단은 진행하지 않음.

  남은 지연 경로:
    기존 기본 프로필은 UPDATE 응답 최대600ms, 제어기 갱신 만료350ms였다.
    단일 응답 지연도 다음 갱신을 막을 수 있다. 타임아웃을 제거해 숨기지 않는다.
    기본 명령 나이300ms와 ROS 서비스 응답 제한250ms도 별도 조건이다.

  현재 공중 Wi-Fi 연속 MANUAL — 소프트웨어·90초 목표0 관찰 통과, 긴 지연 시 보호 정지:
    config/commissioning.yaml: commissioning.manual_timeout_s=2.0.
    최대 명령 나이1.5초 / 브라우저 상태 유효기간1.5초 / HTTP 응답 제한1500ms.
    서버 시각 추정 표본은 최근2초만 사용. 정확한 프로필 정보가 아니면 시작을 막음.
    제어기는 수신 시각에서 명령 나이를 뺀 발행 시각부터 만료를 계산한다.
    늦게 도착한 명령이 새2초를 얻지 않으며, 이미 만료된 세션을 재시작하지 않는다.
    기본값·MOTOR/STEERING 단기 시험의0.35초 이하 감시와 telemetry0.30초·제어 지연0.20초 유지.
    통신 단절 뒤 마지막 명령 시각부터 약2초+제어 주기 최대20ms 뒤 모터0A.
    이전0.35초보다 반응이 늦어질 수 있고 STOP도 전송 지연을 겪을 수 있다.
    공중 고정 시험 후보이며 지상 주행 검증은 없다. Windows/Pi 전체8/8, Windows GUI171개·raw444개 통과.
    목표0·서보0.5000 관찰:90.184초·177표본,error=null. 목표/송신 ERPM0·전류0A.
    상태 조회 RTT 중앙값26.0ms,95백분위279.9ms,최대1111.7ms.
    이후 수동 STOP 전에 START 후 약99.95초에 상태 조회1513.3ms로 제한을 넘겨
    GUI가 세션을 닫음('GUI session stopped'). 긴 통신 지연에 따른 보호 정지가 남아 있음.
    이후 전역 STOP으로 STOPPED_OUTPUT·operator stop·명령0·전류0A와 자동 재시작 없음을 확인.
    실제 바퀴 회전·±0.55 끝단·지상 주행은 이 시험에서 검증하지 않았음.

  Wi-Fi 절전 비교:
    사용자는 계속 Wi-Fi를 사용해야 한다고 답했다.
    Pi의 Power Management:on을 임시off로 변경하고 iwconfig로off를 확인했다.
    재부팅·인터페이스 재시작 뒤에도 유지되는 영구 변경은 하지 않았다.
    임시 SSH 키의 restrict로 PTY 할당이 거절돼 기존 비밀번호 로그인으로
    sudo 인증을 완료했다. 키 제한이나 SSH 서버 보안 설정은 바꾸지 않았다.
    절전 해제만 적용한 목표0·서보0.5000 비교 시험은90초 완료 전에 실패했다.
    관찰 마지막 성공 표본15.74초까지32개 RUNNING, 이후 상태 조회1초 제한 초과로
    스크립트는17.24초에 종료. 제어기 로그는 START 후 약16.73초에 갱신 만료 FAULT.
    저장 표본의 목표·송신 ERPM0, 전류0A였고 이후 GUI에서도0 명령·0A를 확인했다.
    추가 HTTP worker 수정의 Pi 배포 전 결과다. 절전 해제만으로 해결되지 않았으며
    Wi-Fi가 유일한 원인이라고 확정하지 않는다.

9. 검증 범위와 남은 보정
  ±0.55 후보 포함 통합 빌드·검증: Windows CTest 8/8, Pi CTest 8/8 통과.
  Pi 하위 검사: mapping704, raw419, trial159, ROS591, 당시 HTTP13개 통과.
  이후 GUI 명령 시각·STOP 재시작 보호 수정: 가짜 DOM/HTTP127개 검사 통과.
  HTTP worker8개·연결당1개 요청 수정: Windows/Pi CTest8/8, HTTP16개 통과.
  해당 Pi 빌드의 ROS 검사587개, 가짜 GUI 검사127개 통과.
  연결당32개 재사용: Windows/Pi CTest8/8·HTTP18개 통과, Pi ROS593개.
  최신 보수적 GUI 시각 추정: 가짜 DOM/HTTP148개 및 Windows CTest8/8 통과 후 배포.
  이후 공중 Wi-Fi2초 후보: Windows/Pi 전체8/8, Windows GUI171개·raw444개 검사 통과.
  최신 Pi ROS894개 통과. 실제 목표0 관찰은90.184초 통과했으나 약100초에 보호 정지가 발생했다.
  따라서 무기한 연속 제어나 자동 해제 완전 해결을 주장하지 않는다.
  소프트웨어 시험 통과는 실제 저속 회전과 기계적 조향 범위 검증을 대신하지 않는다.

  다음에는 목표·송신 ERPM·VESC 피드백 ERPM·전류와 함께 바퀴의 연속 회전 여부,
  진동·소리·방향을 기록해 안정적인 최소 목표를 결정한다.
  현재 기록만으로 PID 이득 변경이나 duty 제어 전환이 필요하다고 단정하지 않는다.
  현재 FOC 센서 모드 설정은 sensorless(0)이다. 저장된 R/L/flux 값이 현재
  장착 모터를 실제 측정한 값이라는 증거는 없으며 Hall/encoder 배선도 미확인이다.
  지상 속도(m/s)와 서보 명령별 실제 좌우 조향각 측정도 별도로 남아 있다.
