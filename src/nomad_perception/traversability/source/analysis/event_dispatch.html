계산 완료 후 기다리던 발행 경로를 수정했다

C++ 기준본 20261105-1과 Python 기준본 20261105-7은 보존했다. 수치 계산, 점군 DDS 깊이 5, 입력 FIFO와 촬영 시각 및 신선도 기준은 유지한다. 실제 Jetson은 교체하지 않았다.

완료 신호는 즉시 전달하지만, 이미 실행 중인 계산을 강제로 중단하지 않는다. 동일한 지도 상태를 한 실행 흐름에서 변경하기 때문에 ROS 콜백이 바쁠 때의 대기는 남을 수 있다. 최대 갱신 간격 1초를 보장하는 설계라고 주장하지 않는다.

입력과 완료 이벤트는 ROS 실행기 안에서 직렬로 처리한다. 임의로 계산 스레드 수를 늘려 지도에 동시에 접근하지 않았다. 파일 기록 스레드는 지도 계산에 쓰는 상태를 수정하지 않는다.

무엇을 유지하고 무엇을 바꿨는가

  • 입출력 토픽, 사용자 정의 ROS 메시지 6개, 프레임, 외부 보정, 지면과 경사 및 의미 비용 계산식은 유지했다.
  • LiDAR와 OAK의 DDS 대기 5개, 전달 FIFO 80쌍과 8프레임 및 계산 대기 최대 200개는 유지했다. 센서 입력을 최신 1개로 바꾸지 않았다.
  • 계산 결과와 입력 도착은 ROS guard로 알린다. 기존 15ms 입력 폴링은 제거했다. 100ms 타이머는 초기화와 만료 확인 등 유지 관리용이다.
  • 완료된 결과를 새 입력 처리 뒤에서 기다리게 하지 않도록 처리 시작과 프레임 경계에서 확인한다. 의미 사영 같은 한 콜백의 내부 연산을 선점하지는 않는다.
  • 큰 상태 파일의 JSON 직렬화와 파일 I/O를 지도 발행 경로에서 제거했다. 불변 결과를 공유하므로 기록을 위해 전체 지도를 다시 복사하지 않는다.
  • 기록이 느리면 최신 진단 상태 파일만 합쳐 쓴다. 이는 원래부터 최신 상태를 나타내던 terrain/live.json 및 terrain/timing.json에만 해당한다. 입력 관측의 보관과 계산 대기 정책은 바꾸지 않았다.
  • 파일 기록 오류는 진단에 표시한다. 실제 지도 생성은 상태 파일을 다시 읽지 않고 메모리 결과를 사용한다.

단계별 시간도 구분한다

진단 항목측정 범위
worker_to_mapper_receive_ms작업자 계산 완료부터 지도 메인의 결과 수신까지. CBOR 포장과 전달 및 복원을 포함한다.
mapper_event_wait_ms지도 메인이 결과를 수신한 뒤 완료 처리에 들어갈 때까지 대기.
mapper_cost_output_ms완료 처리에서 비용지도 계산과 발행 처리를 호출한 시간. 중복 결과라 발행하지 않은 경우도 구분한다.
worker_complete_to_map_publish_ms실제로 새 촬영 시각의 지도를 발행한 경우의 작업자 완료부터 지도 발행까지.

이 값들은 PC 시험기의 실제 지도 수신 시각까지의 지연과 다르다. 출력 DDS 및 기록기 스케줄 지연은 input_publish_to_map_receive_ms에 포함된다. Python과 C++ 작업자 진단의 측정 범위가 다르므로 그 수치만으로 언어별 배속을 계산하지 않는다.

구현 근거와 남은 범위

다른 스레드가 ROS 대기 상태를 깨우는 연결은 공식 GuardCondition과 Waitable 원본을 따른다. Humble와 Jazzy의 인터페이스 차이는 같은 구현의 어댑터로 처리하고 양쪽에서 시험한다.

이번 수정은 완료 알림과 발행 우선 처리 및 상태 파일 기록의 분리를 대상으로 한다. 점군과 지도 내부의 JSON 자료구조와 CBOR 전달을 전부 전용 이진 구조로 바꾸지는 않았다. 이는 별도의 병목 후보이며 기존 수치 결과를 보존하면서 바꾸려면 추가 대조가 필요하다. 실제 센서 잡음이나 보정 및 주행 안전을 이 가상 시험으로 검증하지 않는다. 실행 관리기의 PID 시작 시각은 에뮬레이터가 합성한 자기 stat 대신 커널의 leader task stat으로 조회하도록 수정하고, 시작 시각과 부팅 ID 및 그룹 확인은 그대로 유지했다.

최초 C++ 전환 기록과 이전 패키지는 보존한다. 최신 선택과 해시는 최종 모듈 기준 19절을 따른다.
