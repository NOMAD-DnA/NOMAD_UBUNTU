# 플래닝 시나리오 실험실

실제 Hybrid A* GPP, RPP LPP, 명령 선택기, Control과 Gazebo 차량 물리를 실행한다.
위치는 Gazebo GT, 지도는 원본 시나리오의 정답 격자를 시야 범위 안에서 점진적으로 공개한다.
이 모드는 플래닝 검증용이다. B0/VIO/GNSS 융합 성능을 포함하지 않는다.

## 실행

작업 폴더 `nomad_ws`에서:

```bash
./scripts/run_scenario_lab.sh
```

2026-10-27 스냅샷을 기본 위치에 복원했다면 위 명령은
`sessions/planning_lab_archives/20261027`의 큐와 결과를 자동으로 읽는다.
복원 폴더가 없으면 기존 `sessions/planning_lab`을 사용한다.
다른 기록을 열려면 `--root sessions/planning_lab`처럼 명시한다.
자동 실험 재실행은 하지 않으며, 큐에서 새 시험을 시작하면 선택한 폴더에 결과를 추가한다.
`--run` 단일 시험의 출력 위치는 기존처럼 `--output`으로 지정한다.

기존 프로젝트 GUI에도 **플래닝 시나리오 실험실 열기** 버튼이 있다.
창만 열면 Gazebo는 시작되지 않는다. 알고리즘은 현재 **Hybrid A* + RPP** 한 가지다.

1. 시나리오·반복 횟수·sim 시간 제한을 지정하고 **큐에 추가** 또는 **6개 모두 추가**.
2. **큐 시작**. 시험은 하나씩 실행하며 종료한 프로세스 정리가 확인된 뒤 다음으로 넘어간다.
3. **실행 중 Gazebo 보기**로 현재 시험 서버에 3D 클라이언트를 연결한다.
4. **시나리오 결과**에서 시나리오와 실행 기록을 선택하면 궤적·속도·장애물 여유 그래프와 지표를 볼 수 있다.
5. **현재 시험 중지 / 큐 일시정지**는 현재 시험을 종료하고 나머지 대기는 보존한다. 창을 닫을 때도 소유 시험을 정리한다.

기본 실험 domain은 **142**다. 일반 실행 domain42와 분리한다.
변경하려면 `NOMAD_SCENARIO_DOMAIN_ID=143 ./scripts/run_scenario_lab.sh`.
`.nomad/env.sh`의 localhost·Gazebo partition 정책을 그대로 사용한다.
명시적 `NOMAD_GZ_PARTITION`이 다른 실행과 같으면 충돌 검사가 실행을 거부한다.
기존 다른 실행을 강제 종료하지 않는다. GUI 재시작 시 실행 중이던 항목은 `interrupted`로 남기며 자동 재시작하지 않는다.

단일 CLI 시험도 가능하다. 출력 폴더는 **새 이름**이어야 한다.

```bash
./scripts/run_scenario_lab.sh --run --scenario 1 \
  --output sessions/planning_lab/runs/manual_01 --timeout 180
```

`--timeout`은 sim초이며 별도로 `max(120, timeout×4)` 벽시계 초의 한도가 있다.
CLI/GUI는 같은 domain의 모듈과 중복 실행을 거부한다.

## 3번 경사각 선택 (2026-10-27)

GUI에서 **3번 시나리오 → 지형 최대 경사각(0~30°, 기본 5°) → 큐에 추가**를 선택한다.
각도를 바꿔 여러 항목을 추가하면 각각의 값이 큐에 고정된다. 이미 추가한 항목이나 실행 중인 시험은 변경되지 않는다.
`6개 모두 추가`에서도 3번에만 이 설정을 적용한다. 결과 표의 `최대 경사` 열에서 조건을 구별한다.

```bash
./scripts/run_scenario_lab.sh --run --scenario 3 --slope-deg 8 \
  --output sessions/planning_lab/runs/slope8_새이름 --timeout 180
```

- 선택각은 언덕 전체의 일정한 각도가 아니라 **생성된 삼각형 지형의 최대 경사각**이다. 기존 언덕 범위 x=7~17m, y=4~12m와 곡면 형태를 유지하고 높이를 조정한다.
- Gazebo의 실제 두 삼각형/셀에서 각각 경사를 계산하고 큰 값을 해당 셀의 경사로 사용한다. 지형 최대각을 매번 실측 계산하여 기록한다.
- 새 설정의 3번은 기존의 고정 합성 지면 비용을 대체한다. 관측된 통행 가능 셀에서 `p_s=min(경사/10°,1)^2`, GPP 단위거리 비용은 `1+5*p_s`이다. 기존 `PlanningCostLayers`와 `gpp.cost_mode=multi`를 사용하며 별도 GPP를 만들지 않는다.
- **10° 이상은 차단값 80**, 기존 벽은 100으로 유지한다. 이 10°는 실험의 판정 기준이며 실제 차량 등판 한계가 아니다. GT 경사이므로 인지단의 반복 관측 확정 과정을 시험하는 모드는 아니다.
- 관측된 셀에만 경사·지면 계층을 제공한다. 미관측 셀은 지도 -1, 특징 NaN을 유지한다. LPP에도 같은 차단 지도와 경사 기반 0~79 비용을 전달한다.
- source `grid`는 물리 벽/가시선용, `planning_grid`는 지형 비용/차단용이다. 경사 차단 셀을 Gazebo 수직 벽으로 만들지 않는다.
- `map/scenario.json`·`map/provenance.json`·`manifest.json`·`config.yaml`·`outcome.json`에 지형/비용 조건을 보존한다. 결과 그림은 당시 저장된 지도를 읽는다.
- 기존 기록과 `--slope-deg` 없는 CLI는 기존 0.30m 언덕·합성 비용을 유지하고 GUI에 `기존 지형·합성비용`으로 구별한다. 새 조건과 동일 조건의 반복 실험으로 합산하지 않는다.

변경 파일: scenario_lab의 core.py/worlds.py/runner.py/worker.py/gui.py, terrain_profile.json 및 관련 테스트.
기본각·입력범위·차단기준·경사가중치는 terrain_profile.json에 모아 두고 실행별 설정/manifest에 확정한다.
검증: 생성 OBJ 법선으로 최대각 0/5/10/20/30° 검증, 기존 GPP 비용 합성·차단·미관측 보존,
GUI 큐별 설정 고정/CLI 전달 및 기존 시나리오 회귀 검증. 실행 검증 결과는 아래 후속 기록을 따른다.
복구: 기존 조건은 `--slope-deg`를 생략해 재현한다. 기존 맵·데이터·모델·플래닝 알고리즘은 덮어쓰지 않는다.

## 지도와 시나리오

| 번호 | 환경 | 기대 결과 |
|---|---|---|
| 1 | 넓은 직선 통로, 출발과 목표의 측면 차이 | 목표 도착 |
| 2 | 넓은 길의 단일 장애물 | 우회 후 목표 도착 |
| 3 | 짧은 고비용 구간과 더 완만한 우회 공간 | 비용을 반영한 경로로 목표 도착 |
| 4 | 연속 S자 통로 | 연속 조향으로 목표 도착 |
| 5 | 굽이 뒤 통로를 막는 벽, 우회 연결 없음 | 벽 관측 후 정지; 목표 미도달 |
| 6 | 앞이 막힌 좁은 포켓, 목표는 뒤쪽 | 전진 경로 부재로 정지; 목표 미도달 |

원본은 `src/nomad_bringup/nomad_bringup/scenario_lab/authoring.json`이다.
HTML의 30cm·80×54 격자, 출발·목표, 장애물 셀과 비용을 보존했다. 미리 계산한 주행 궤적은 사용하지 않는다.
`worlds.py`는 차단 셀의 정확한 합집합을 높이 1.3m의 정적 장애물로 만들고 기존 차량의 질량·조인트·구동·마찰 설정을 사용한다.
각 실행 폴더의 `map/world.sdf`에 새 맵이 생성된다. 기존 maps1–8과 개인 ABCD 백업은 수정하지 않는다.

기존 기록 및 경사각 미지정 CLI에서는 HTML에 3D 높이가 없으므로 3번에만 x=7~17m, y=4~12m의 최대 0.30m 완만한 곡면을 명시적으로 추가했다.
**이전 HTML 비용은 합성 시험 입력이며 이 곡면의 실측 경사에서 다시 계산한 값이 아니다.** 새 GUI 경사각 선택은 위의 메시 기반 비용 모드를 사용한다.
따라서 3번은 비용 반영과 경사진 지면의 물리 주행을 시험하며, 실제 인지의 경사 추정·차단 임계 검증은 후속 통합 시험에 해당한다.

지도 입력은 차량 반경 7.5m의 방사형 LOS 관측이며 벽 뒤는 unknown(-1)으로 남는다.
카메라 시야각·증거 누적·감쇠를 모사하지 않는다. 6번에는 뒤쪽 출구를 관측한 과거 위치(5,8)의 정답 관측을 명시적으로 제공한다.
미관측 후방 전체를 free로 채우지는 않는다.
실험 설정은 같은 디렉터리의 `config.yaml`이며 실행마다 복사한다. 생산용 인지/위치추정 설정은 바꾸지 않는다.

## GPP 발행 정책과 로그

`observed_corridor` + `corridor.retain_safe_path: true`에서 정상 경로를 검사하면
`/nomad/corridor_status`에 `state=validated_safe_path`, `publication=none`만 발행한다.
`global_path`와 동일한 `navigation_target`은 재발행하지 않는다. LPP는 캐시한 경로를 추종한다.
경유점 도달·최종 목표 전환·무효화·추종 조건 이탈·실패 후 재시도에서는 필요한 새 경로를 발행한다.
동일 좌표의 중간 목표는 경로만 바뀌어도 다시 발행하지 않는다.

유지 조건은 기존 코드와 같다: 경로와 차량 간 위치 차이 ≤25cm, 방향 차이 ≤15도,
현재 지도에서 남은 경로·목표의 유효성, 최신 입력 등의 조건이다.
‘장애물 없음’만으로 모든 재계획이 생략되는 것은 아니다.
LPP/Control의 짧은 명령 유효기간과 정지 검사는 유지한다.
빈 경로를 발행한 뒤에는 유효한 참조를 다시 발행해야 추종을 재개한다.

각 실행의 `events.jsonl`에는 경로 발행과 GPP 검사·후보·선택·무효 원인이 sim 시각과 함께 남는다.
`gpp.log`, `lpp.log`, `selector.log`, `control.log`, `gazebo.log`는 해당 시험의 실행 로그다.
일반 GUI 로그 저장 정책과 별개로 사용자가 명시적으로 시작한 실험의 결과/진단 파일만 저장한다.

| 기대 결과 | 1~4는 도착, 5는 벽 관측·1m 이상 진행 후 GPP 진행 불가와 5sim초 정지, 6은 GPP 진행 불가와 5sim초 정지. 외곽 겹침이 없어야 함 |
| 장애물 여유 p05 | 약 10Hz sim 표본에서 차량 중심 기준 반길이 .52m/반폭 .40m 회전 사각형과 GT 장애물 사각형 사이 XY 최소 거리의 5백분위 |
| 외곽 겹침 | 위 보수적 외곽 거리가 0일 때 즉시 종료. 접촉 센서의 충돌력 측정과는 다름 |
| CPU | GPP/LPP 각 프로세스 `/proc` user+system CPU 누적 차이, 단위 core·s. 기록기 첫 CPU 표본~종료 구간이며 내부 함수 시간/CPU 비율/GPU 사용량과 다름 |
| 주행 시간/시각 | 목표 전송 후 기록된 sim 경과 시간, 실행 시작 UTC ISO 시각, 별도 wall 경과 시간 |
| GPP 발행 수 | poses가 있는 `global_path` 수. 빈 경로 정지 신호는 별도 집계 |
| 무효 후 재계획 수 | 지도 차단·경로 자세 이탈·LPP 실패 등 무효 판정 이후 성공적으로 새 경로를 발행한 수. 최초 발행·정상 경유점 전환·실패한 탐색 횟수와 구분 |

결측값은 null/—이며 0으로 채우지 않는다. 40sim초 동안 10cm 이상의 진척이 없으면 `stalled`, 시간 한도는 `timeout`, 입력/프로세스 오류는 별도 결과다.
1회 도착은 반복 시험의 신뢰도나 실차 안전성 검증을 뜻하지 않는다. 원본 HTML과 달리 실제 물리·RPP 추종 오차 때문에 재계획 횟수와 경로가 달라질 수 있다.

## 결과와 재현

`sessions/planning_lab/queue.json`에 큐를, `runs/<실행ID>/`에 다음을 보존한다.

- `manifest.json`: 시나리오·입력 방식·domain/partition·시간 제한·사용 소스 SHA256
- `config.yaml`, `map/`: 실행 설정, SDF/OBJ/원본 격자와 생성 출처
- `trajectory.csv`, `events.jsonl`, `outcome.json`: 원시 표본, 이벤트, 집계 결과
- `ownership.json`, `runner.json`: 소유 프로세스와 정리 확인
- 파트별 로그와 `timing/`: 실패 조사 및 내부 연산 시간 표본

시험 결과는 생성물이므로 Git 추적에서 제외한다. 영구 비교에 사용할 실행 폴더는 별도 백업한다.
