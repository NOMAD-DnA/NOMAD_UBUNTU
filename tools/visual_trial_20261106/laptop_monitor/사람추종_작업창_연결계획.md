# 사람 추종 작업창과 Jetson 연결 계획

작성: 2026-11-13. 이번 반영은 공유 GUI의 **작업창만**이다. 보드 소스·설정·실행 파일·ROS 계약은 변경하지 않았다.

## 지금 사용할 수 있는 화면

1. 기존 GUI에서 **플래닝 개발 → 사람 추종 작업창**을 연다.
2. 왼쪽은 기존 `PlanningMap`으로 전역 지도, 차량 위치·윤곽, GPP 경로, LPP 궤적, 이동 경로를 표시한다. 확대·이동·표시 토글이 가능하다.
3. 오른쪽은 메인 GUI가 이미 받은 원본 영상(`rgb`)과 의미분할 영상(`semantic`)이다. 새 SSH/ROS 구독·보드 프로세스를 만들지 않는다.
4. 사람 선택·추종 시작·추종 종료는 **미연결 상태로 비활성**이다. 플래너 연결만으로 활성화되지 않는다. 지도 클릭도 목표를 선택하거나 전송하지 않는다.
5. 이 창을 열거나 닫아도 기존 수동 목표/플래닝 실행은 유지된다. 실제 주행 중지는 기존 플래닝 창의 출력 정지를 사용한다.
6. 관전·기록 재생에서도 화면만 볼 수 있다. 영상과 지도는 수신/촬영 시각 및 오류 상태를 보존한다. 화면의 사람을 추적하거나 실제 거리를 계산한 것처럼 표시하지 않는다.

실시간 데이터가 없으면 빈 화면/미수신 표시가 정상이다. 현재 카메라 미리보기는 흑백일 수 있다. 원본과 분할 영상은 별도로 수신되므로 같은 프레임이라는 보장이 없다.

## 추후 배치: 사람 추종 계산도 Jetson

```text
Jetson 기존 의미분할 + Pi5 OAK 깊이 + 촬영 시각 TF/보정
                ↓ (기존 발행 출력을 읽기만 함)
Jetson 새 사람 추종 모듈 [예정, 미구현]
  사람 후보 좌표 생성 → 선택 대상 추적 → 거리 유지 목표 생성
                ↓
Jetson 플래닝 입력 관리자 [예정, 미구현]
  수동 목표 / 사람 추종 단일 소유권 + 관측 만료/연결 단절 검사
                ↓
           기존 GPP → LPP → 제어

PC GUI ← 후보·상태·프레임 식별자 ← Jetson 사람 추종 모듈
PC GUI → 대상 선택 / 시작 / 종료 → Jetson 사람 추종 모듈
```

PC는 표시와 사용자 의도 전달만 담당하고, 사람 위치·추적·목표 갱신은 Jetson에서 계산하는 방향이다. 기존 공유 `NOMAD_사람추종_PC_20261113`의 Python 코드는 상태/추적/목표 생성 규칙과 테스트의 참조 구현으로 활용한다. 보드의 C/C++ 정책에 맞춰 포팅·검증해야 하며 이번 GUI는 해당 PC 모듈도 실행/import하지 않는다.

현재 분할 추론을 재사용하는 방안이며 새 신경망을 추가한다고 가정하지 않는다. Jetson 전체 CPU/GPU 여유와 실시간 부하는 아직 확인되지 않았다. 배치 적합성은 실제 영상 주기·추종 지연·플래너 주기와 함께 계측해야 한다.

## 실제로 빠진 연결부

- GUI의 `semantic`은 표시용 압축 색상 영상이다. 여기서 색을 읽어 사람 클래스나 실제 거리를 확정하지 않는다. 보드 원본 라벨 `/perception/semantic/class_ids`를 사용해야 한다.
- 현행 field12 설정의 사람 ID는 1이다. 다른 모델을 사용할 때는 출력 클래스 계약을 다시 검증한다. PC 합성 예제의 ID 7을 실차에 적용하지 않는다.
- OAK `/oak/depth/points`와 ZED 라벨은 서로 다른 광학 좌표계다. 기존 보정과 촬영 시각 TF를 재사용해 대응시켜야 하며 단순 픽셀 인덱스 결합은 불가하다.
- 현재 보드의 `SensorRig`/`PoseSource` 계산은 재사용 후보다. 보정 파일이 존재하는 것과 움직이는 사람의 위치가 정확히 추정되는 것은 별개의 검증이다. 가림·배경 깊이 혼입·시간차를 처리해야 한다.
- 새 사람 관측 생성은 인지 성격의 기능이다. 기존 인지 노드를 수정해야 하는 상황이 나오면 사용자 조건에 따라 멈추고 변경 범위를 먼저 설명한다. 이번 작업은 새 보드 모듈 추가/설치 승인이 아니다.
- 기존 `goal` API에는 사람 관측 만료와 추종 세션 계약이 없다. 동적 좌표를 `goal`로 계속 재전송하는 것만으로 연결하지 않는다.

## GUI 코드의 연결 위치

| 파일 / 함수 | 현재 | 추후 연결 작업 |
|---|---|---|
| `developer_planning.py` → `PlanningWindow._open_follow_window()` | `person_follow` 창 열기만 수행 | 진입 동작 유지. 창 열기로 모드/출력 권한을 바꾸지 않음 |
| `monitor.py` → `open_developer_window()` | 단일 창 생성/재사용, 기존 스냅샷 공유 | 사람 추종도 같은 수신 경로 사용. 새 중복 수신기 금지 |
| `monitor.py` → `developer_snapshot()` | 기존 지도·영상·플래닝 상태 제공 | 검증된 `follow_ui`/후보 관측 상태를 추가할 예정 |
| `developer_person_follow.py` → `PersonFollowWindow.update_snapshot()` | 읽기 전용 지도·영상·미연결 표시 | 후보 상자·선택 대상·거리·LOST/HOLD 등 보드 상태 표시 |
| 같은 창의 `select_button`, `start_button`, `stop_button` | disabled, 전송 슬롯 없음 | 기능 버전 협상/신선한 관측/운용 권한 확인 후 controller 슬롯에 연결 |
| 같은 창의 `panels['rgb'/'semantic']` | 기존 `ImagePanel`, 클릭 처리 없음 | 표시 비율·여백을 역변환한 원본 픽셀과 **그 표시 프레임 식별자**로 선택 요청 |
| `planning_client.py` → `send()`, `read_output()`, `display_event()` | 기존 명령과 플래닝 상태만 처리 | 같은 SSH 세션을 재사용한다면 명령·상태 검증을 명시적으로 확장. 지금은 변경 없음 |
| `relay.py`, 기록/재생 입력 검증 | 기존 스트림만 허용 | 새 상태를 관전·기록에 표시하려면 allowlist/스키마/재생 초기화까지 함께 검증 |
| `remote/jetson_planner.sh` | 현재 런처 유지 | 추후 모듈의 실행·종료 책임과 경로가 정해진 뒤 별도 검토. 이번에는 변경 없음 |

새 버튼을 기존 `send_goal()`에 바로 연결하면 안 된다. 후보 선택과 목표 보내기는 다른 계약이다. 표시 영상은 `t` 부동소수점 시각만 갖고 있으므로 아래 정수 시각·세션 식별자를 임의로 만들어 채우지 않는다. 미래 관측 패킷과 이미지가 동일 capture인지 명시적으로 맞춰야 한다.

## 예정 인터페이스 — 아직 토픽/메시지/명령으로 등록되지 않음

아래는 설계에 필요한 최소 정보이며 기존 보드가 받는 API가 아니다. 이름과 전송 방식은 추후 버전 계약으로 확정한다.

**Jetson → GUI 후보 관측**

- 프로토콜 버전, 모듈 시작마다 바뀌는 `source_session`, 증가하는 `seq`.
- 실제 `capture_ns`(정수 ns), 영상 식별자·소스·크기, 좌표계 `odom`.
- 후보별 `candidate_id`, 화면 bbox, 사람 위치 `(x,y,z)` m, 관측 품질. `track_id`는 추적기가 동일인 연속성을 보장할 때만 제공.
- 선택된 대상, 상태(IDLE/SELECTED/FOLLOWING/HOLD/LOST), 사유, 관측 나이, 실제 계산한 거리, 활성 목표 ID.

**GUI → Jetson 사용자 요청**

- 선택: 요청 ID + 표시한 `source_session/seq/capture_ns` + 후보 ID 또는 원본 픽셀. 오래된 프레임·겹친 후보는 거부.
- 시작: 명시적으로 선택된 대상과 세션 참조. 요청 수신 ACK와 실제 FOLLOWING 상태를 구분.
- 종료: 해당 추종 세션 취소. 중복 요청은 같은 결과로 처리. 요청을 보냈다는 이유만으로 정지 완료 표시하지 않음.
- 일반 플래너 연결 여부만으로 기능을 활성화하지 않음. 구버전 보드는 미지원으로 표시. 관전/재생은 전송 경로 자체가 없어야 함.

**Jetson 추종 → 플래닝 입력 관리자**

- `replace_goal`: 충분히 이동한 새 목표만 GPP에 전달. 현재 새 goal은 경로 무효화/재계획을 유발하므로 갱신 주기·이동 문턱 필요.
- `retain_goal`: 같은 목표를 유지하며 원래 관측의 유효성만 확인. GPP에 같은 목표를 계속 새로 넣지 않음.
- `stop`: 추종 목표 취소. 사람을 놓침/관측 만료/세션 변경/연산 정지 시 이전 목표로 계속 주행하지 않도록 보드가 판단.
- 관측 원본 시각과 단조 시계 watchdog을 모두 사용. heartbeat가 오래된 관측을 새 관측으로 만들면 안 됨.
- 수동 목표와 추종은 한 번에 하나만 소유. ROS `/goal_pose`와 SSH 목표 등 모든 진입점에 동일한 규칙을 적용.
- GUI 종료/통신 단절/작업창 닫기/모듈 재시작의 종료 정책도 보드까지 구현. 이번 미리보기 창의 닫기는 명령을 보내지 않지만, 실제 추종 통합에서는 명시적인 해제·watchdog 정책이 필요함.
- 기존 출력 허용(arm)을 자동으로 누르지 않음. GPP/LPP 충돌 검사와 제어 watchdog은 그대로 사용.

거리 유지 2m, 목표 갱신 최소 1초/이동 0.3m, 관측 만료 1.5초 등 앞서 만든 PC 모듈의 값은 **초기 시제품 설정**이다. 실차 안전거리·성능으로 확정된 값이 아니다. 초기 범위는 시야 내 한 사람, 놓치면 정지·재선택이며 재식별/가림 뒤 자동 재추종은 별도 작업이다.

## 나중에 통합할 때 확인할 순서

1. 주행 출력 없이 원본 영상·후보 상자·사람 좌표·촬영 시각 정렬을 확인한다.
2. 클릭한 프레임이 실제 선택 요청과 일치하는지, 겹친 사람·배경·낡은 화면을 거부하는지 확인한다.
3. 목표 제안만 기록해 거리 유지와 갱신 빈도를 확인한다. 아직 모터 출력은 허용하지 않는다.
4. 통신 단절, 관측 중단, 세션 교체, 시계 역행, 중복/역순 패킷에서 보드가 추종 목표를 해제하는지 확인한다.
5. 기존 수동 목표와 관전·재생 회귀 검사 후, 별도 실차 시험 범위를 정한다.

## 이번 검증 범위

합성 스냅샷을 사용한 오프라인 Qt 검사: 창 열기·재사용, 기존 영상/지도 공유, 읽기 전용 동작, 지도 클릭이 목표가 되지 않음, 플래너가 연결돼도 추종 버튼은 비활성, 오래된/오류 영상 및 재생 시간 역행 처리. 새 작업창 검사 5개 + 기존 개발 창 검사 30개 + 플래닝 회귀 검사 40개, 총 75개가 통과했다. Python 3.8 문법 호환 검사와 합성 입력 화면 렌더 확인도 완료했다. 실제 Jetson 연결·사람 추적·실차 주행 검증은 이번 범위에 포함하지 않는다.
